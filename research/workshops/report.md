### Висновок

**Спільне в усіх трьох:** CLAUDE.md і rules, субагенти, skills, хуки, ідея context engineering. Усі три адресовані розробникам із досвідом і навчають за схемою «агент пише код, людина контролює». Усі три стверджують, що важливі контроль і перевірка, а не «магічні промпти».

**D проти трьох інших:** спільного з A–C майже немає. D вчить, як влаштовані самі LLM і як будувати з них системи (RAG, embeddings, агенти). A–C вчать керувати готовим агентом Claude Code.

**Унікальне:**
- **A** — розбір механіки під капотом: системний промпт, «settings ≠ контекст», 33 події хуків, prompt injection через tool results, евали. Практика на TypeScript і чужих харнесах (Pi, Flue, Hermes).
- **B** — повний цикл розробки фічі: PRD → ADR/C4 → задачі → TDD → паралельні агенти. Також Agent Teams, Ralph loop, економіка моделей.
- **C** — єдиний із повним контуром перевірки (типи → лінтер → тести → CI-гейт), агентом у проді (read-only observability, інциденти) і таксономією «що коли». Плюс plan mode і чекпоінти (як згадка).
- **D** — теорія LLM (трансформер, токенізація, sampling, причини галюцинацій), RAG і embeddings, no-code автоматизації на n8n, продакшн-економіка (latency, KV-cache, routing). Орієнтир — кар'єра ML/AI-інженера.

### Який ближчий до твоїх задач

Твоя задача — інтеграційний інженер, не продакшн-розробник: агентний сетап із human-in-the-loop, безпека, Jira/Confluence через MCP, API-тести.

1. **A — найближчий за змістом**, але не за форматом. Блоки 03–06 (settings vs контекст, CLAUDE.md, хуки, що модель реально бачить) прямо відповідають твоєму хуку «не слати партнерам без підтвердження» і безпеці. Практика (TS-репозиторій, чужі харнеси, Flue) тобі майже не потрібна. З дня 2 корисні лише блоки 13–14 (контекст і субагенти, евали).
2. **C — найближчий за структурою**: з нього виріс твій план, і він покриває перевірку та безпеку. Але написаний для людей із 3+ роками продакшн-коду. Найцінніше з нього (контур перевірки, рев'ю, «зелений ≠ працює») ти вже забрав у план.
3. **B — далеко.** Він про розробку фічі в коді (PRD, ADR, vertical slices, TDD). З нього корисні лише ідея gate-точок і «MCP overload» (Jira + Linear + Notion), бо Jira/Confluence в тебе саме через MCP.
4. **D — найдалі від поточних задач.** Це інший напрям: розуміння LLM і побудова власних LLM-систем, а не керування Claude Code. Під твій план з нього корисні дві ідеї: «коли агенти — оверкіл» і failure handling в автоматизаціях з HITL. Решта (трансформер, RAG, embeddings) знадобиться, лише якщо захочеш переходити в ML/AI-інженерію.

Жоден курс не розрахований на QA/інтеграційного інженера: потрібне доведеться адаптувати.

**Застереження щодо сторінок A, B і D.**

### b) Що взяти з A, B і D

**З A (взяти):**
- **Принцип «прохання ≠ закон»** (CLAUDE.md можна проігнорувати, хуки і permissions ні). Це теоретична основа твого хука з підтвердженням → Т5–Т6.
- **«Settings ≠ контекст» і «deny-правило забирає тул із контексту цілком».** Практично: заборонені MCP-тули не з'їдають контекст → Т4–Т5.
- **«Текст у контексті»:** prompt injection через файли і результати тулів, великі результати в файли → Т3, Т6.
- **Евали як спосіб міряти:** маленький набір реальних випадків partner-tracker із очікуваним результатом. Перевіряєш, що зміна справді допомогла, а не «здалося» → Т7.
- **Ергономіка нагляду:** «де зупиняється, чи видно план, чи можна відкотити». Готовий чекліст для рев'ю → Т8.

**З A (пропустити):** власний харнес на Flue/TypeScript, Pi, DeepSeek Harness, Hermes, Meta-Harness. Не під твої задачі.

**З B (взяти):**
- **Gate-точки** («місця, де інженер каже ок чи не ок»). Лягає на HITL → Т6.
- **MCP overload** (кілька трекерів одночасно: модель обирає інструмент «мовчки»). Тестуй на своєму Jira + Confluence MCP → Т4.
- **Ідея «CLAUDE.md пишеш сам і ростеш від болю»** (на сторінці її подано як висновок дослідження, я це не перевіряв). Можна взяти як практику: керуватися ним при аудиті Т1.
- **Шаблон «специфікація → задачі → тест-план»** для онбордингу нового партнера (№11) як структура фінального проєкту → Т8.

**З B (пропустити):** Ralph loop, Agent Teams, PRD/SAD/ADR/C4, vertical slices, TDD як процес. Це про розробку фіч.

**З D (взяти):**
- **«Коли агенти — оверкіл»** (урок 11). У таблицю таксономії Т4 додай варіант «без LLM, звичайний скрипт». Частина функцій partner-tracker (наприклад, збір статусів за шаблоном) може не потребувати агента → Т4.
- **Failure handling поряд із human-in-the-loop** (воркшоп 12). Що робить потік, коли MCP/канал недоступний або відправка впала: має зупинитись і сказати, а не тихо повторювати → Т6.
- **Offline vs online eval** (урок 13). Твій евал-набір у Т7 — це offline eval. Онлайн-аналог: фіксувати, як часто ти правиш чернетки агента перед відправкою → Т7.
- **Причини галюцинацій** (урок 5) як теоретичне обґрунтування «доказів замість звіту» в Т8. Опційно: в офіційній документації Claude Code цієї теорії немає, тож це читання поза планом.

**З D (пропустити):** трансформер і attention, токенізація в деталях, SFT/RLHF, embeddings, RAG, n8n. Це база для ML-інженера, а не для твого сетапу на Claude Code.

### Обмеження звіту

- Ціна C і формат C (живий чи запис, дати) на сторінці відсутні. Сторінку «Ціни» і форму консультації не відкривав.
- Зміст пунктів Plan mode / чекпоінти / effort / resume у C відомий лише з короткого опису блоку, не з назв 15 тем.
- Скріншоти C, A, B — стан після розгортання останнього акордеона (панелі відкриваються по одній); повний текст усіх панелей — у `.txt`. На D акордеонів немає, скріншот показує всю сторінку.
- Ціна і формат D (живий чи запис, дати) на сторінці відсутні. Форму «Залишити заявку» не відкривав.
- Дані A–C зібрано 27.10, D — 29.10. Ціни B на 27.10; воркшоп B стартує 29.10.
- Вердикти про ціну/цінність і розподіл по тижнях — мої оцінки, не факти зі сторінок.
